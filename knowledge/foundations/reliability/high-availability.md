# HA：高可用

## 一句话解释

HA（High Availability，高可用）是让系统在约定的故障范围内，仍持续或快速恢复提供满足要求的服务，从而达到可用性目标的设计与运行能力。

## 工作原理

高可用关注用户能否完成业务操作，不能仅以进程存活判断。常见机制包括：

- **冗余与故障隔离**：把实例分散到不同主机或可用区，避免一次故障影响全部副本。
- **检测与切换**：健康检查发现故障后，摘除实例、切换主备或重新路由流量。
- **状态保护**：有状态服务通过数据复制与一致性机制支持接管；接管时需防止多个节点同时认为自己是主节点的“脑裂”。
- **恢复与验证**：修复故障副本，监控业务成功率，并演练切换是否真的有效。

例如，两个 API 实例分布在不同主机上，一个宕机后入口将请求转给另一个，且剩余实例能承载流量，才形成对单机故障的有效容错。入口、数据库和共享存储也必须检查是否存在单点故障。

## 如何衡量

按时间衡量时：`可用性 = 可用时间 / 观察总时间`。假设连续服务且一年按 365 天计算，99.9% 对应约 8.76 小时不可用预算，99.99% 对应约 52.56 分钟。真实目标必须明确观察窗口、成功标准，以及计划维护是否计入。

也可按有效请求成功比例衡量；它与时间比例不是同一口径。系统需要先定义 SLO（服务等级目标），再评估架构和运行结果是否满足它。

## 适用边界

- 多副本并不自动等于 HA：副本可能共享故障点，切换可能失败，剩余容量也可能不足。
- HA 不意味着零中断或零数据丢失；恢复时间和允许的数据损失应分别明确。
- 备份用于恢复历史数据，不能直接替代在线接管；复制也可能同步误删，不能替代备份。
- HA 与灾难恢复（DR）的边界取决于设计覆盖的故障范围：常规故障通常由 HA 处理，大范围灾难通常依靠 DR，两者需要共同规划。

## 实践意义

先明确需要承受“进程退出、单机宕机还是整个可用区故障”，再确定冗余和恢复机制。nohup 解决挂断信号，systemd 可恢复单机服务进程，完整 HA 还要覆盖依赖、流量、状态和故障域。
