# 阿里云 AgentCore 产品调研

## 研究背景与结论

本次研究用于建立企业 Agent 平台的产品知识基线，重点回答平台定义、架构职责、配置化定制和运行托管四个问题。查阅日期为 2026-10-10，依据滚动更新的官方文档，未开通实例、未执行部署或性能实验。`active` 表示文档证据已核对，产品行为仍会演进，不表示完成生产验证。

AgentCore 是阿里云的智能体构建和治理平台。它将工作空间中的 Agent、模型与工具资产、协作和运行配置组织在统一控制台中。AgentCore 是平台，QwenPaw／Qoder 是托管 Harness 的执行引擎，模型连接提供模型访问配置，四者不能混为同一个产品。[A1][A2]

对企业平台设计最值得借鉴的是资源组织和运行组织的区分：Workspace 组织可复用资产，Agent 描述执行单元，实例承载进程，Session 组织连续交互，Team 组织协作。它提供配置化和代码部署等入口，但不同模式不拥有完全相同的能力。[A2][A3]

## 产品边界

| 模式 | 用户提供 | 平台负责 | 边界 |
|---|---|---|---|
| 托管 Harness | 引擎选择、角色、模型、绑定资产和资源配置 | Harness 运行和实例／会话管理 | 引擎能力和当前支持项约束定制范围 |
| 高代码 Agent | 应用代码、容器镜像、启动与服务契约 | 镜像托管运行、资源与平台接入 | 应用负责业务逻辑与框架状态 |
| 本地 Agent 纳管 | 已有部署与接入配置 | 统一管理和协作接入 | 纳管不等于云端替用户维护原部署 |

以上来自基本概念和部署指南。注册／纳管功能是否在目标地域可用，须以具体控制台和接入指南确认。[A2][A4]

## 本次研究回答

- 架构层次：官方公布能力分组和资源对象，尚未找到完整内部服务拓扑或统一“七层”定义。见[架构分析](architecture.md)。
- 定制能力：可以配置托管 Harness，也可以编写代码，二者约束不同。见[定制与托管](customization-and-hosting.md)。
- 企业托管：包含资源、会话、网络、存储与权限入口，不能据此认定任务断点恢复、业务操作幂等或全部合规要求已由平台完成。
- 开发基础：官方明确 Harness 使用 QwenPaw／Qoder，SDK 适配多个框架。未确认平台直接基于 AgentRun、函数计算或 Kubernetes，未确认平台源自 OpenClaw 或其他产品。

## 适用判断

**研究判断：**已有阿里云资产、需要统一工作空间和办公渠道接入的团队，可优先验证此产品。涉及持久知识、长期记忆或审批的业务，应首先核对具体模式，不能从产品概述的应用场景推导托管 Harness 已支持这些能力。

不对 AWS 与阿里云做性能、稳定性或成本排序，本次没有相同工作负载实验。两家同名不构成代码继承证据。
