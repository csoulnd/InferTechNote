# Dify 定制与托管责任

## 低代码能力的定位

可视化 Workflow 让作者显式组合模型、检索和工具；Agent Node 的策略扩展把自主决策放在局部步骤；新的 Build Mode 进一步允许通过对话积累配置与技能。[D1][D4][D5] 三者属于不同定制粒度，不应把生成技能、拖拽节点与框架编程统称为同一种低代码。

研究判断：Dify 对流程作者更直接，而 AgentCore 更强调托管与服务接入。两者有重叠，但不能依据界面体验判断生产韧性或性能领先。

## 部署责任矩阵

| 模式 | 谁运营 | 需要单独核对 |
|---|---|---|
| Cloud | 服务商运营平台 | 套餐、数据位置、额度及合同 |
| Community 自部署 | 用户运营全部组件 | 数据备份、扩缩容、镜像升级、插件权限、网络 |
| Enterprise 私有部署 | 按购买和交付约定 | SSO、RBAC、隔离策略、支持范围与 SLA |

官方列出 Enterprise 的 SSO、RBAC 与支持能力。[D1][D9] “可以 Docker Compose 启动”只证明部署入口存在，不能证明具有自动容灾和生产 SLA。

## 数据与恢复

应用配置、对话、上传文件、知识索引和 Agent 工作目录需要分别纳入备份策略。runtime 的 Home snapshot 文档明确表示 restore 不是事务，途中失败应重建环境；它也不是业务流程与外部系统的联合事务。[D7]

队列重试是否重新调用已完成工具、审批能否跨重启恢复、租户数据是否越权，都需要运行级验证。源码中有持久化与隔离组件不代表这些组合属性自动成立。

## 许可边界

仓库标注 Dify Open Source License，以 Apache 2.0 为基础附加条件；许可文件另列多租户服务和前端标识相关条款。[D2] 选型记录应引用原文并核对计划用途，不能只标“Apache-2.0”。此处记录条款存在，不替具体商业用途作法律判断。
