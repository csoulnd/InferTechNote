# 产品调研

先读根 AGENTS.md 和产品索引，检索已有研究。报告放在 agent/investigations/products/<product>/；基础文档与网站展示分开。

## 研究主线

先回答产品面向谁、解决什么核心问题、侧重点与边界是什么；再解释软件架构怎样支撑这一定位。判断它是应用平台、Harness、编排框架、运行平台还是其中多个组件的组合。功能表、低代码能力、企业托管和费用只用于解释设计，不替代定位与机制分析。

软件架构应串起核心组件及职责、一次典型请求的执行路径、状态和生命周期、控制与执行职责、实现基础及设计取舍。说明为什么这样组织、获得什么、付出什么；厂商未公开或本轮未走读的部分明确留下未知项，不用推测填满架构图。

## 文档形态

默认每个产品只保留两份完整文档：

- summary.md：可独立阅读的摘要。讲清产品定位、核心侧重点、关键架构关系、实现依据与主要取舍，并链接 detail.md。不要写成只有目录的入口。
- detail.md：连贯的详细报告。推荐顺序为定位与边界 → 软件架构 → 典型执行路径 → 定位与架构的关系及取舍 → 辅助能力／部署边界 → 未知与待验证 → 来源。组件图、来源登记、版本基线及 Knowledge Extraction 均放在本篇。

短产品研究可以直接用一篇完整文档，无须制造内容重复的摘要。不要为了分类把一个产品拆成 architecture、customization、hosting、sources 等章节文件；报告可读性优先。仅在用户要求或形成独立稳定问题时再提炼到 knowledge/，产品报告不强制原子化。

迁移旧报告时用 git mv 保留主要路径历史，合并原始证据、限制与验证记录，修复所有引用及系列索引。来源应在文内可点击追溯；单篇仍只有一个 H1。不要把章节文件留作第三、第四份正文。

## 证据与边界

优先查官方文档和源码，登记来源支持范围、查阅日期、代码提交或版本。区分官方定位、文档机制、源码事实、研究判断和待实测项。仅阅读 README／部署清单不称作完整源码走读。重新组织报告时保留原始证据日期，选择性复核注明哪些来源已更新。

架构图注明是官方图还是依据公开职责重建的研究视图；逻辑角色不意味着物理服务已经分离。SDK 适配、协议兼容与示例仓库不能证明平台基于相应框架。新执行路径、仓库迁移和同名产品需核对范围，main 和实验性 API 不冒充稳定版本。

按实际模式分析：配置式 Harness、自带代码、本地纳管；Community、Cloud、Enterprise；纯库、宿主、商业平台。能力不能跨模式借用。控制面、数据面、遥测位置及 LICENSE 分别记录。

状态分开看会话历史、文件、长期记忆、图检查点、活进程与外部副作用；检查恢复从哪里开始、哪些动作重跑、由谁去重。内存示例后端不能证明跨进程恢复，扩展钩子不能证明 OS 隔离。

历史模块清单、架构分析维度和当前能力分别记录；并列服务不画成依赖层。没有同负载实验，不评价性能、成本或稳定性胜负；待验证项说明问题与观测目标。

## 完成与迭代

用户指定研究顺序时，先实际完成一个产品，再把本次有证据的可复用纠错规则纳入技能，继续下一个。保持技能简洁，不将厂商瞬时功能清单固化为通用要求；系列索引记录迭代缘由。

交付前检查两篇的职责、主线和链接，运行 git diff --check 与仓库知识审计。技能修改后运行 skill-creator 的 quick_validate.py（Windows 中文文件可使用 python -X utf8）。提交和推送遵循当前用户授权。
