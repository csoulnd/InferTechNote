# 服务部署与测试工作区

把部署和测试工程维持为少量明确目录，用户能直接使用服务和测试工具的原生入口。适用于单机、多机及容器环境，不绑定模型、硬件、用户名、地址或测试工具。

## 少量输入与范围

优先从本会话、现有README、脚本和只读现场获取以下信息，仅询问无法可靠推断的必要项：

- 目标机器及工程绝对路径；不同机器的角色，路径是否共享。
- 本次意图：仅检查、新建、整理归档、清理，或后续部署测试。
- 已存在的权威配置、设备发现/rootinfo、工具环境、源码、数据路径。
- 需要回传的记录保存到哪个本地或独立归档位置；未指定时在本地工程外建立明确命名目录，并告知路径。

同一会话的路径和授权持续有效，不重复索要已给出的信息。调用本技能不会自动授权删除未知文件、重启服务或重新发压。用户已明确要求归档后清理时，完成核验与回传后继续执行该范围，不额外设置确认关卡。“先检查/区分”仅做只读分类。

切换服务器必须重新探测路径、服务归属和文件引用，不沿用旧机器的PID、磁盘、IP、容器或共享存储假设。

## 默认目录与职责

```text
<project>/
├── scripts/                 # 服务部署、停止入口；按部署模式分目录
├── test-configs/            # 可执行原生测试配置、输入、必要生成配置
├── log/
│   ├── services/            # 按服务启动批次保存完整原生日志
│   └── tests/               # 按测试点、轮次保存工具原生日志及结果
└── README.md                # 唯一操作说明、目录约定与最小批次对应表
```

- 服务目录可为 `services/<模式>/<角色-启动时间-编号>/`。多机同名批次在README记录主机与角色，不默认为共享目录。测试目录可为 `tests/<测试点>/<round-XX>/<warmup|measurement>/`；工具原生时间戳子目录保留。
- 每次服务启动保留一份完整标准输出/错误日志；服务自身生成的运行时日志另保留，不能把不同日志流误认为重复。按请求ID和时间定位轮次，不默认复制窗口切片或另存session副本。
- 测试日志仅保存工具原生日志、逐请求结果、性能CSV/JSON/HTML及工具自身配置快照。工具原生元数据属于原生结果，不因扩展名为JSON而删除。
- 测试输入与可编辑配置进入test-configs，服务脚本进入scripts；不把数据体积称为日志体积。
- 不默认创建助手调度日志、外层command/case/exit-code文件、采样快照、分析结论、清单JSON或压缩包。必要的助手操作记录放在工程外独立目录，不混入用户日志。
- 不自动分析性能或介质命中率。用户明确触发时才分析；必要证据不足就说明不可核验，不能事后虚构采样或用时延代替命中证据。
- 不为了目录整齐移动或删除运行必需状态。服务锁优先使用适合该系统的运行时目录；已有应用要求固定位置则保留并在README说明最小例外。

README仅记录机器/角色、权威外部路径、部署与原生测试命令、批次和轮次位置、未执行/无效批次标识及必要限制。不额外生成交接、索引、清单和总结多份文档。若已有详细分析，应按用户要求回传工程外后再清理。

## 原生日志与辅助文件的判定

按“内容生产者、当前文件的保存方式、用途”分类，不仅看后缀或文件名：

| 内容 | 处理原则 |
|---|---|
| 服务stdout/stderr、服务/硬件运行时日志 | 原生日志；启动器重定向不改变其归属 |
| 原生测试工具执行输出和结果目录 | 保留原生内容，避免重写历史结果 |
| 服务日志切片、采样、原生日志压缩包 | 由助手收集；不是新的服务日志源；先核实原件是否完整再处理副本 |
| 指标差值、命中比例、有效性标记、汇总 | 助手派生结果；需要时回传，清理服务器副本 |
| coordinator/driver、命令JSON、时间戳旁路文件 | 助手调度或执行元数据；默认取消 |
| 数据、配置、原生manifest | 复现材料，单独存放；manifest可能绑定原路径，不能谎称迁移后仍可直接执行 |
| 混合console输出 | 查看内容；不能因文件是助手重定向的就整体丢弃原生证据 |

## 已有现场的整理与清理

1. **检查现场。** 枚举限定工程范围内的结构、占用、软链接；查看相关进程环境、工作目录、文件句柄、容器挂载以及脚本/任务引用。识别其他任务占用。目录存在、PID文件或旧README不证明服务仍从这里运行。
2. **明确保留与清理集合。** 按上述来源分类。没有打开的句柄不等于没有后续依赖，还需检查配置及脚本路径。对旧项目、工具环境、源码、数据分别判断，不因共用父目录批量删除。完整原生日志未找到时，不能把唯一切片或压缩包当作已确认重复。
3. **先回传。** 用户要求先回传的分析、历史或辅助材料，先复制到本地或指定独立位置并核验SHA256/文件完整性。可临时打包传输，但不要把永久压缩包留在服务器用户工程；验证后移除临时传输包。只为本次所需材料归档，不默认把权重和整个依赖环境复制一遍。
4. **归位并校验。** 整理到目标结构；移动文件核验内容未变。只更新供后续执行的配置与脚本中的路径；原生历史结果保持原文。测试配置引用的数据必须存在，部署脚本完成适当的静态检查。
5. **最后清理。** 只删除用户授权范围内、已确认可清理的具体目标。递归操作前核验绝对路径、父目录及软链接边界，不跟随链接删除外部文件。未知归属、仍有活动写入、回传校验失败或无法保证日志完整时，只停止受影响目标，继续不受影响的整理并说明原因。
6. **收尾。** 检查目标结构、原生结果保留、配置引用、外部依赖和临时文件；README写清当前状态。简短报告保留项、删除项、回传路径、验证范围及是否重启。不要把静态校验称为真实部署/性能验收。

运行中的服务默认不为清理而重启。不要直接删除正在写入的日志；如果要迁移，先核验服务的日志重开/轮转能力及已有授权。无法无损迁移时暂留原件，README注明待下一次正常重启归位，避免默默截断或丢日志。

## 配置单一来源

当用户指定外层权威配置目录时，让部署脚本直接引用该位置。统一前逐机比较内容；有差异时保留证据并确定适用值，不以某台机器的配置覆盖全部机器。rootinfo/拓扑/设备发现文件尤其必须保留各机身份。

工程内无需维持第二份可编辑配置。是否暂留链接或备份依据用户选择；明确要求不留旧文件时，删除已确认的旧副本/兼容链接及本次迁移备份。已有进程可能已加载旧内容，路径修改并不代表运行状态已改变；无授权不自动重启。

## 后续执行保持简洁

- 优先使用已安装工具的原生CLI与配置，不为了统一目录再包一层发压调度器。核验现场版本支持的参数，显式区分数据准备、warmup、正式测量和分析。
- 并发、请求数、输入输出长度、预热与轮次规则来自本次用户需求；不把曾使用的4C、三轮、128K/1K或缓存比例固化为通用要求。
- 原生工具自带warmup是否复用正式数据应核实。涉及缓存时说明对初态的影响；独立预热与原生warmup不是自动等价。
- 一次启动后多轮可代表连续窗口，但不能宣称缓存初态相同。是否每轮/每候选重建初态由测试目标决定。
- 修改启动器使新日志直接进入目标目录，不额外落盘助手PID/退出码/调度记录；必要运行锁和工具原生状态不受此限制。
- 保留失败与排除轮次原始证据；README仅标明状态，不把未执行的配置目录算成完成结果。

- “新服务器C，工程 /srv/test-lab，沿用 $service-test-workspace，只初始化目录和说明，不启动服务。”
- “按 $service-test-workspace 检查这个工程，先列清理项，不删除。”

用户给出机器和根目录后尽量从现场补齐细节；不要求用户每次重复整套约定。
